# 웹페이지 설계 논리 — 제안 v0.1

2026-11-15. 사용자 요구는 재질 이미지 모음이 아니라 **페이지를 구성하고 조작하게 하는 논리**다.
아래는 검증할 설계 제안이며 확정된 민호의 취향 규칙이 아니다.

## 1. 정보가 형태보다 먼저

페이지마다 ‘사용자의 목적 / 먼저 알아야 할 것 / 다음 행동’을 한 문장씩 적는다.
대표 행동 하나를 정하고 보조 행동은 시각적으로 구분한다. 읽는 순서와 DOM 순서를 일치시킨다.
장식 때문에 주요 정보나 조작이 가려지면 표현을 줄인다.

## 2. 배치의 기준점

제목·본문·목록·조작부가 공유하는 정렬축을 먼저 잡는다. 카드로 모든 것을 쪼개지 않는다.
관계가 가까운 정보의 간격은 작게, 구역 간 간격은 크게 둔다. 크기 수치는 시험 후 결정한다.
좁은 화면에서는 중요도가 낮은 부가정보를 상세로 옮긴다. 핵심 행동을 삭제해서 맞추지 않는다.
고정 가장자리 탐색은 실험 가설이다. 콘텐츠 공간·모바일·키보드 순서에서 손해가 있으면 일반 탐색과 비교한다.

## 3. 타이포그래피

- 기존 Figma의 Miedinger(사용자 발음 기반 영문 표기, 정확한 패밀리·웨이트 확인 필요)와 Montserrat를 후보로 삼는다.
- 제목·본문·레이블·수치의 역할을 분리하고, 큰 글자와 가는 글자의 대비가 실제 읽기 위계를 돕는지 평가한다.
- 한글 폴백은 영문과 높이·무게·행간을 함께 비교한다. 가는 제목을 긴 본문에 그대로 적용하지 않는다.
- 실제 폰트 파일과 웹 사용 권리 확인 전에는 파일을 저장소에 넣거나 CDN에 배포하지 않는다.
- 현재 Fable 실험안은 시스템 폰트 스택이며 위 두 서체의 적용 결과가 아니다.

## 4. 조작의 문법

각 부품에 기본 / hover / focus-visible / 선택 / 비활성 / 오류 상태를 필요에 따라 정의한다.
선택과 hover를 혼동하지 않고, 색 이외에도 선·텍스트·형태로 상태를 드러낸다.
목록 선택 → 상세 확인 → 닫기 → 원래 항목으로 포커스 복귀를 한 흐름으로 설계한다.
펼친 메뉴는 Escape와 바깥 클릭, 키보드 접근을 검증한다. 실제 저장이 없으면 시연임을 명시한다.

## 5. 색·재질·움직임은 역할에 종속

배경 / 표면 / 본문 / 보조문 / 경계 / 포커스 / 선택 / 오류처럼 역할 이름부터 정한다.
민트·검정·유리·모따기는 확정 정체성이 아니다. 흑백·불투명 상태에서도 위계가 유지되는지 확인한다.
유리는 뒤의 맥락을 남겨야 하는 일시적 레이어에서 먼저 시험하고 본문 가독성을 해치면 쓰지 않는다.
움직임은 위치·상태 변화의 연결을 설명할 때 사용한다. reduced-motion에서도 조작은 성립해야 한다.

## 6. 같은 규칙을 다른 페이지에서 검증

읽기 페이지(장문·링크) / 작업 페이지(목록·선택·상세) / 전시 페이지(이미지·설명)를 비교한다.
구조는 달라도 글자 역할·정렬·상태·피드백이 같은 언어를 쓰는지 본다.
특정 화면의 연출을 모든 제품의 보편 규칙으로 만들지 않는다.

## 판단 기록 양식

문제 → 시안 → 그렇게 한 이유 → 사용 조건 → 사용하지 않을 조건 → 실제 화면·조작 근거 → 사용자 피드백.
현재 문서는 계획이며 접근성·가독성·모바일 품질을 통과했다는 인증이 아니다.
